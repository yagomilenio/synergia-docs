## Requirements

* Python >= 3.10 (tested with Python 3.14.4).
* Docker installed and available in the `PATH`.
* `perf` installed, with a *paranoia* level ≤ 2 (see below).
* Access to a Synergia server instance (REST API + WebSocket API).

## Installation

Since the client is published on PyPI, the most recommended and direct option is to perform a clean installation with `pip`:

```bash
pip install synergia
```

If you prefer to install it from source code or plan to develop on the client, clone the `synergia-client` repository and install it in editable mode:

```bash
git clone https://github.com/yagomilenio/synergia-client.git
cd synergia-client
pip install -e .
```

Either method will register the `synergia` command in your system (the `pyproject.toml` file declares it under `[project.scripts] synergia = "client.client:main"`), installing all required dependencies in the process.

## System Configuration: `perf`

The client uses `perf` to measure the CPU cycles consumed by each task — this is the basis of the [credit cost calculation](../modelo-economico/#fórmulas-de-cálculo-de-coste-de-ejecución). By default, the Linux kernel restricts its use to `root`. It is necessary to lower the *paranoia* level to 2 or less:

```bash
# Temporary (until next reboot)
sudo sysctl kernel.perf_event_paranoid=2

# Permanent
echo 'kernel.perf_event_paranoid=2' | sudo tee /etc/sysctl.d/99-perf.conf
sudo sysctl -p /etc/sysctl.d/99-perf.conf
```

Installing `perf` by distribution:

| Distro | Command |
|---|---|
| Debian/Ubuntu | `apt install linux-perf` |
| Fedora/RHEL | `dnf install perf` |
| Arch | `pacman -S perf` |

:::note[Without `perf`, the worker cannot measure its own consumption]
If `perf_event_paranoid` remains above 2, the client will be unable to read the actual CPU cycles consumed during task execution, which prevents correctly calculating the cost to settle. Verify the current value with `cat /proc/sys/kernel/perf_event_paranoid`.
:::

## Local Configuration Files

The client maintains three state files in the user's `home` directory. Only one of them is edited manually.

### `~/.config/synergia/config.ini` — editable

Contains the connection URLs to the Synergia server. It must be modified to point to the server instance you want to use (ngrok, own domain, public IP, etc.):

```ini
[rest]
base_url = https://tu-servidor.ngrok-free.app
base_port = 443

[ws]
base_url = wss://tu-servidor-ws.ngrok-free.app
base_port = 443
```

This file is mounted as a volume inside the worker's Docker container, so it can be modified on the fly without rebuilding the image. It is not necessary to restart the container if it was already running — the change is applied on the next run.

### `~/.cn_profile.json` — autogenerated

Automatically generated when running `login-user`, `login-google`, or `login-github`. It contains the JWT token of the active session. It is not necessary (nor recommended) to edit it manually.

### `~/.cn_device.json` — autogenerated or manual

Generated with `synergia configure-device`. It contains the hardware resources that the node offers to the network:

```json
{
    "cpu_threads": 8,
    "gpu_device": 0,
    "ram": 16384
}
```

It can be generated via autodetection (`synergia configure-device`) or by specifying the values manually:

```bash
synergia configure-device --cpu-threads 8 --gpu-device 0 --ram 16384
```

## Project Structure

```
synergia-client/
├── client/
│   ├── client.py                  # Main CLI, definition of all commands
│   ├── config.py                  # Session, device, and config.ini loader
│   └── scheduler.py               # Automatic scheduler (round-robin / split)
├── worker/
│   ├── worker.py                  # Subscription and task execution logic
│   ├── docker_util.py             # Worker Docker container management
│   ├── Dockerfile                 # Execution container image
│   ├── container/
│   │   ├── config.ini             # Server URLs (mounted as a volume)
│   │   ├── upload_results.py      # Script to upload results to the server
│   │   ├── hash_util.py           # SHA256 hashing utilities
│   │   ├── iptables.sh            # Container network rules (blocking outbound traffic)
│   │   ├── curl_wrapper.c         # curl wrapper with download logging
│   │   └── wget_wrapper.c         # wget wrapper with download logging
│   └── utils/
│       ├── configuration_interpreter.py   # Interpreter for the task repo config.toml
│       ├── github_util.py                 # Utilities for GitHub repos
│       └── logger.py                      # Logger with Rich
├── tests/
│   ├── test.sh                    # Integration test for the consensus system
│   ├── create_tasks.sh            # Script to create test tasks
│   └── tasks.txt                  # List of test tasks
├── pyproject.toml
└── requirements.txt
```

## Typical Usage Flow

**As a publisher** (publishing a task):

```bash
synergia login-user --username miusuario --passwd mipassword
synergia create-task --name "Mi tarea" --github-url https://github.com/user/repo
synergia task-info --task-id 1
synergia output-task --task-id 1 --download
```

**As a worker** (running others' tasks and earning credits):

```bash
synergia login-user --username miusuario --passwd mipassword
synergia configure-device
synergia find-task --status ACTIVE
synergia subscribe-task --task-id 1
```

**Automatic mode with scheduler:**

```bash
# Run all subscribed tasks in round-robin
synergia start-scheduler --mode round-robin

# Run in parallel using all available cores
synergia start-scheduler --mode split

# Only use CPU that the system is not using
synergia start-scheduler --mode round-robin --on-idle
```
