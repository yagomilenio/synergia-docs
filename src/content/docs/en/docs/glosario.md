This page gathers the terms used throughout the documentation. If something is not clear on another page, it is a good idea to start here.

---

### Task

A unit of work published by a user on the platform. To define each task, a GitHub repository containing all the code necessary to execute the computationally expensive process is required. This repository must have a pre-defined structure, consisting mainly of two files: a `config.toml`, which specifies the task's characteristics and requirements, and a `Makefile`, responsible for the direct execution of the code and acting as the entry point for processing.

Not all tasks are the same; there are two main types (which must be specified in `config.toml`):

* **Static:** The total number of inputs is known at the time of publication and does not vary unless changes from GitHub are re-synchronized with the platform. The platform automatically partitions all inputs into blocks when creating the task.
* **Dynamic:** The number of inputs is not pre-defined, and new inputs can be added in real time. Useful in continuous workflows — a clear example is running an LLM, where the typical case is being able to query it in real time.

Tasks can be in one of five states throughout their lifecycle: **ACTIVE** (active, allowed to be processed), **PAUSED** (temporarily suspended, usually due to insufficient publisher balance or by self-decision), **CANCELLED** (cancelled by the publisher), and **COMPLETE** (manually closed in dynamic tasks, or automatically in static tasks when the specified total number of inputs is completed).

### Input

Data or subset of data that requires computing power to be processed. When various unrelated inputs are supplied, they can be distributed for parallelization — this is what Synergia symbolizes.

### Block

The minimum unit of processing and publication. It corresponds to the grouping of a task's inputs. The number of inputs per block depends directly on the total number of inputs: if this exceeds a certain threshold, the block size increases to save memory on the servers. Nodes processing a task can combine multiple blocks and process them at once — they are indivisible units, but joinable at the result publication level: a single combined result produced by joining multiple blocks of the same task can be uploaded. This is a design consideration implemented directly to minimize the network bandwidth required for communications. Both static tasks with few inputs and dynamic tasks receive the minimum block size, equivalent to one input per block.

### Process

A record representing the assignment of one or more blocks to a worker for processing. A process exists from the moment a first node processes one or several blocks and publishes its results. From then on, nodes wishing to re-process any of the blocks contained in this process must process all the blocks contained in that process.

Each process contains information about the range of inputs it covers (grouped into blocks), the hash of the repository at the time of task creation, and the execution currently considered canonical. The process is the central entity of the cross-verification mechanism, as it allows comparing the results of different nodes on the same data blocks.

### Canonical Result

The verified and accepted result for a specific process, established by consensus among the executions of different nodes. When two independent nodes process the same blocks with the same execution environment and produce the exact same result file (verified by its SHA-256 hash), that result is established as canonical. All nodes whose execution matches the current canonical result receive a payment in the form of credits and reputation, derived from the number of confirmations and the initial payment generated by processing that process.

An execution is considered canonical when it was the first execution of the process that yielded the result currently considered valid — that is, the one with the highest number of **confirmations** (a confirmation occurs when, in an already completed process, it is executed again to compare results). If a result does not match the current canonical one, the possibility of a canonical change is evaluated; if it remains as it was, a penalty is added to the reputation of the discrepant node, and it receives no credits.

### Credit

The internal unit of exchange on the platform. Credits have no external monetary value (they are not cryptocurrencies, nor can they be exchanged for real money): they represent computing capacity. Users obtain credits by contributing their hardware as workers, and consume them when publishing tasks (payments are made both during the publication process and when other nodes process their tasks).

### Reputation

A numerical value associated with each account reflecting its history of behavior on the platform. It is automatically recalculated after each canonical change, penalizing workers whose results are replaced by those of others and rewarding those who consistently produce correct results.

Reputation is used to mitigate potential attackers, forcing them to recover it before processing new blocks of other users' tasks. They will also be unable to publish new tasks, and their current ones will be paused. To recover their reputation, a user must perform a certain number of valid confirmations. See the full formula in [Economic Model](../modelo-economico/#weighted-reputation-algorithm).

## Summary Table

| Term | Short Definition |
|---|---|
| Task | Published unit of work, defined by a GitHub repository with `config.toml` + `Makefile`. |
| Input | Individual data to process within a task. |
| Block | Minimum grouping of inputs published and processed. |
| Process | Assignment of one or more blocks to a worker, the central unit of cross-verification. |
| Execution | Specific processing attempt of a process performed by a worker. |
| Canonical Result | Result accepted by consensus among executions of different nodes. |
| Credit | Internal unit of exchange without external monetary value. |
| Reputation | Indicator of an account's historical trustworthiness. |
